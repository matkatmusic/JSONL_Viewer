RevEng Reconstruction Engine — Pipeline

Input: a Claude Code session transcript (.jsonl)  →  Output: the reconstructed edit history of every file the session touched. Entry point: src/reconstruction_cli.ts :: runCli(argv)

The whole engine at maximum zoom-out. In C++ terms: a pure transform pipeline — vector<TranscriptRecord> flows in, gets enriched into vector<FileEvent> per file, folds into vector<FileRevision>, and one of several renderers stringifies the result. The only I/O is reading the transcript, the backup blobs, and (optionally) shelling out to git/python3. Click any step to jump to the matching steps in the 15-step view.

Same pipeline, one level down. Steps 8–14 are the interesting part: inside reconstructFileOver() the event list is rewritten by a fixed-order chain of repair passes (think: successive passes over an IR in a compiler). Each pass is a no-op unless it finds something to fix, and every pass marked ⛁ silently skips when there is no BackupReader. Click any step to jump to the matching functions in the full call graph.

scripts/check_scenario_coverage.ts is the engine's integration-test harness. For every executed scenario it asks: can the engine, given only the session JSONL(s) + file-history backups, byte-for-byte reproduce the ground-truth snapshots captured in .step_states/step-NNN/? The dashed box is the engine boundary — the only functions the checker imports from src/. Note the deliberate seam: the checker injects its own cross-session BackupReader through reconstructStepStates(records, reader?) instead of using the engine's single-session default.
