### B.1 Behavior (plain English)

The linter validates a `.txt` scenario before `run-all-scenarios.py` / the
run-scenario skill processes it. It parses the file with the same function the
runner uses — `runScenario_convertTxtToJson` in
`common/scripts/run_scenario_lib.py:374` — so the linter can never disagree
with the runner about what a step means. It prints one line per finding
(`<file>: step <N>: <message>` or `<file>: header: <message>`) and exits 1 if
there is at least one finding, 0 otherwise (print `OK` per clean file).
Multiple file arguments are allowed; exit 1 if any file has findings.

### B.2 Checks

1. **Header fields** — `session`, `model`, `ponytail` each non-empty in the
   parsed dict (every current scenario carries all three; verified s1, s44,
   s87). One finding per missing field.
2. **No unknown steps** — any parsed step with `action == "unknown"` is a
   finding; include the offending payload text.
3. **Written numbers match parse order** — the parser's `step_num` is the
   count of `- [`-prefixed lines, but authors also write a literal number
   (`- [ ] 12. Say ...`). Re-read the file (same `split("---", 1)` body rule
   as the parser), and for each line starting `- [` extract the written
   number with `re.match(r"^-\s*\[[ x]\]\s*(\d+)\.", line)`; a mismatch
   between the written number and the 1-based enumeration order is a finding.
   (A step line with no number at all already surfaces as `unknown` via
   check 2 — do not double-report it here.)
4. **Agent-target simulation** — replicate the executor's state machine from
   `runScenario_executeSteps` (run_scenario_lib.py:892). Before coding this,
   read the `elif action == "spawn":` branch of that function and mirror its
   naming exactly; the `spawnconcurrent` branch is
   `agent_index += 1; name = payload.strip() or f"a{agent_index}"`. Simulate:
   - start: known agents `{"a1"}`, `active = "a1"`, `agent_index = 1`;
   - each step resolves `target = step["target"] or active`;
   - a step whose EXPLICIT `target` is not in the known set at that point is
     a finding ("targets unspawned agent") — this covers `Say @aN` and every
     other targeted verb;
   - `spawn` / `spawnconcurrent` register the new agent name and make it
     active; every other step makes its resolved target active (exactly as
     the executor does).
5. **Exit and Record per agent** — after the walk, every known agent must
   have at least one `exit` step and at least one `record` step that resolved
   to it; one finding per missing pair member, per agent.
6. **Rewind payloads** — for each `rewind` step: the payload must match
   `re.fullmatch(r"\d+(?:,\s*\S.*)?", payload)` (the `<N>[, code]` form);
   if it matches, `N` must be ≤ the number of prior `say`/`sayqueued` steps
   that resolved to the same target agent. Each violation is a finding.

### B.3 Structure

Single script, stdlib only. Import the parser by inserting the repo root
(`Path(__file__).resolve().parents[1]`) at the front of `sys.path`, then
`from common.scripts.run_scenario_lib import runScenario_convertTxtToJson`
(same import root the tests already use; the `external/` submodules it pulls
in are present in the working clone). Suggested function names (verbs,
≤15 lines each — filesize_check enforces this):

- `lintScenario_checkHeaderFields(parsed) -> list[str]`

- `lintScenario_checkWrittenStepNumbers(text) -> list[str]`
- `lintScenario_walkAgentTargets(parsed) -> tuple[list[str], dict]` — returns
  findings plus the per-agent tallies (says / exits / records) the later
  checks consume
- `lintScenario_checkExitRecordPerAgent(tallies) -> list[str]`
- `lintScenario_checkRewindPayloads(parsed, saysBeforeStep) -> list[str]`
- `lintScenario_lintFile(path) -> list[str]`
- `main() -> int`

If the walk function cannot stay within the 15-line/function limit as one
