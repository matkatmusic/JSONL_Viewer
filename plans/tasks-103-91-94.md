## Phase A — Task 94: snapshot-jump button appears only for snapshot-backed revisions

The `⤷` button (webapp/views/timeline-render-chips.ts:187-203) renders whenever
`computeSnapshotJumpRoute` (webapp/views/timeline-changes.ts:104) resolves a route — i.e. for any
changeId matching any surviving revision. Decision: it must render only when the revision is
actually backed by a File History Snapshot. A revision is snapshot-backed exactly when its
changeId is a backup blob name (`<hex>@vN`); tool-evidenced revisions carry `toolu_…` ids.
The blob-name pattern already exists inline in `findRevisionForChangeId`
(webapp/views/file-history-model.ts:97: `/^(.+@)v\d+$/`) — that file is the pattern's canonical home.

## Phase B — Task 91: disambiguate colliding rename badges inline

`renderFileTreeLeaf` (webapp/views/sidebar.ts:111-117) renders `← <basename(originalPath)>`; two
renames from the same basename are indistinguishable. Decision: disambiguate inline with the
shortest distinguishing suffix of the old path, only when badges would otherwise collide.
The label is computed in the DOM-free view-model (`webapp/views/timeline-file-tree.ts`, already
tested by `tests/timeline-file-tree.test.ts`) and stamped on `FileSidebarEntry`, so both producers
(sidebar list and the details pane's per-node tree) get it and the renderer stays dumb.

### B1. RED — tests in `tests/timeline-file-tree.test.ts`

Use the file's existing `makeFileEntry`-style fixture helpers (extend the helper with an
`originalPath` parameter if it lacks one). Add:

1. `test_rename_badge_labels_keep_basename_when_unique`:
   entries renamed from `/root/src/old_a.py` and `/root/docs/old_b.py` → after
   `applyRenameBadgeLabels(entries)`, labels are `old_a.py` and `old_b.py` (no collision → bare
   basename), and an entry with `originalPath: undefined` keeps `renameBadgeLabel: undefined`.
2. `test_rename_badge_labels_extend_to_shortest_distinguishing_suffix_on_collision`:
   entries renamed from `/root/src/utils.py` and `/root/docs/utils.py` → labels are
   `src/utils.py` and `docs/utils.py` (one extra segment is the shortest distinguishing suffix).
3. `test_rename_badge_labels_extend_past_equal_parent_segments`:
   `/root/a/pkg/utils.py` vs `/root/b/pkg/utils.py` → labels `a/pkg/utils.py` and
   `b/pkg/utils.py` (depth grows until the suffixes differ, not just by one).
4. `test_buildFilesSidebarViewModel_stamps_rename_badge_labels`:
   build a `WireTimelineDocument`-shaped input (same wire-shape style as the file's existing
   tests) with two histories whose first rename revisions come from same-basename paths; assert
   both entries carry the disambiguated labels — proving `buildFilesSidebarViewModel` applies the
   helper, not just that the helper works.

### B2. GREEN — `webapp/views/timeline-file-tree.ts`

1. `FileSidebarEntry` gains
   `renameBadgeLabel: string | undefined;` with comment: the badge's inline text — the shortest
   suffix of `originalPath` distinguishing it from every other rename badge in the same list;
   bare basename when unique; undefined when the file was never renamed (task 91).
2. Add and export `applyRenameBadgeLabels(entries: FileSidebarEntry[]): void`:
   - Collect the entries whose `originalPath !== undefined`.
   - Per entry keep a suffix depth, starting at 1 (basename). Compute a label as the last
     `depth` segments of `originalPath` joined with `/`.
   - Loop: group entries by current label; for every group holding two or more DISTINCT
     originalPaths, increment the depth of each member whose label can still grow (depth <
     its segment count); recompute; stop when no group changed a depth (two identical
     originalPaths legitimately share a full-path label — the loop must terminate, not spin).
   - Stamp each collected entry's `renameBadgeLabel`.
   - Keep the helper and its private pieces verb-named and single-condition-per-branch.
3. `buildFilesSidebarViewModel`: build the entry array (each literal now includes
   `renameBadgeLabel: undefined`), call `applyRenameBadgeLabels(entries)`, return it.

### B3. Second producer — `webapp/views/details.ts` (~line 40-56)

The per-node "Files touched" tree builds fresh `FileSidebarEntry` literals

## Phase C — Task 103: badge failed git commands as FAILED (red)

Extraction (src/reconstruction_git_operations.ts) never reads the tool_result's `is_error`
(the field already exists on hydrated tool_result blocks — src/structures/content-blocks.ts:30).
Decision: never suppress — every timeline row a failed git command produces gets a red `FAILED`
badge. Failed git commands surface in TWO row kinds: commit nodes (from `gitOperations` via
`deriveCommitNodes`) and the `* git … *` tool-call rows (from `toolCalls`, joined to gitOperations
by the Bash record's uuid). CommitMarkers stay untouched (decision: badge, not suppress).

the retry add/commit results do not. The C1 test's expected vector below assumes this; correct
the vector to the fixture's reality if the grep says otherwise.
