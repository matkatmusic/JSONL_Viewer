### Step 1.4 — green: `jfred/src/layered_merge.ts` (new, ~90 lines)

Algorithm, in this order:

1. **Flatten.** For each `sessionTimeline`, for each node: skip
   `LayeredNodeKind.endState` and `LayeredNodeKind.presumedUserEdit` (both are
   re-derived at merged level — end state is deduped, gaps are recomputed
   because another session's beacon may explain a gap this session could not).
   Collect `{ node, sessionFile }` pairs AND record `sessionFile` in a
   `Map<TimelineNode, Path>` keyed by object identity (`ownerBySessionNode`).
2. **Capture one end state.** The first `endState` node found across the
   session timelines (`findMergedEndStateNode`). `// ponytail: sessions all read
   one disk, so the first end state is the end state; a per-session disagreement
   would be a loader bug, not a merge case.`
3. **Sort** the flattened nodes with `sortNodesOntoAxis` (step 1.1), then append
   the end-state node POSITIONALLY last — same rule as
   `completeLayer1Timeline`'s "appended, not sort-inserted".
4. **Re-derive gaps** by calling `insertPresumedUserEditGaps(nodes)` from
   `layered_end_state.ts` on that node array. Reuse, do not reimplement.
5. **Wrap** each resulting node: `sessionFile = ownerBySessionNode.get(node)`
   (absent → `undefined`, which is exactly right for the end state and for
   freshly inserted gap nodes).
6. **Mark corroboration.** `listSessionsByContent(pairs)` builds
   `Map<string, Path[]>` from content → distinct session paths (dedupe by
   `toString()`), using `checkNodeCarriesBytes` to select content-carrying
   nodes and reading `content` off them. Then per merged node that carries
   bytes: look up its content group; if the group has FEWER than 2 distinct
   sessions, `corroboratedBy = []`; otherwise the group's sessions minus this
   node's own `sessionFile` (an `undefined` own session subtracts nothing, so the
   end state is corroborated by every session that observed those bytes).

Exported surface: `mergeSessionTimelines(entity: ReconstructionEntity): MergedTimeline`
only. Do NOT add a graph-level wrapper — task 207 calls this per entity.

## Item 2 — task 186 (spec S11): per-file sweep harness

### Deliverable

`jfred/scripts/per_file_sweep.ts` — runs the proven task-182 per-file path over
a candidate list against the claude-data sources and emits a markdown results
table plus a resumable JSONL result log. It does NOT run the 68-file sweep;
that run is task 187.

### Why in-process, not one CLI spawn per file (bind the implementer to this)

The attempt-4 evidence (`plans/166-per-file-target.md`) shows the expensive
work is the shared script-run/lineage machinery, memoized per RECORDS-ARRAY
identity. Loading the records ONCE and calling the fast path per candidate over
that same array reuses those caches across candidates; spawning the CLI 68
times would pay the ~11-minute cost 68 times. So: one process, one records
array, N targets.

## Item 3 — task 188 (spec S12 prep): prove the reconstruct → commit → re-seed loop

### Target and safety

File: `common/scripts/plate/plate_cli.py` (the task-182 proven target, 34-revision
ladder). Baseline `793e65241902f276caf5f5c28d539269e7d36d11`.
**Never write to `~/Programming/jot`.** All commits land in a scratch clone
under the session scratchpad. Reads of the real repo are fine.

### Why re-seeding recovers more (the mechanism to demonstrate)

`--repo`+`--base-commit` seeds revision 0 from the commit's blob
(`gitBase:<hash>:<target>` changeId) and `computeSkippedBaselineCutoff`
(`src/reconstruction_base_commit.ts:52`) drops records BEFORE the baseline
commit's committer time. So committing revision N at revision N's own instant
and re-seeding there moves the window forward: iteration 2 starts from verified
bytes at revision N and continues past it. Therefore the commit MUST be stamped
with the revision's timestamp (`GIT_AUTHOR_DATE` + `GIT_COMMITTER_DATE`), or the
cutoff lands in the wrong place.

### Step 3.1 — scratch clone

```
SCRATCH=<session scratchpad>/jot-loop
git clone --shared ~/Programming/jot "$SCRATCH"      # alternates: source objects stay read-only
git -C "$SCRATCH" checkout -B loop-proof 793e65241902f276caf5f5c28d539269e7d36d11
```

`--shared` because the 25 MB repo needs no object copy and the source is only
ever read.

### Step 3.2 — iteration 1 (bounded to revision 5)

Run in the BACKGROUND (attempt-4's full run took ~11 min; a bounded run is
cheaper but not instant), stderr to a log:

```
cd jfred
npx tsx src/reconstruction_cli.ts \
  ~/Programming/jot-recovery/claude-data/projects/-Users-matkatmusicllc-Programming-jot/*.jsonl \
  --file /Users/matkatmusicllc/Programming/jot/common/scripts/plate/plate_cli.py \
  --repo ~/Programming/jot --base-commit 793e65241902f276caf5f5c28d539269e7d36d11 \
  --fhsLoc ~/Programming/jot-recovery/claude-data/file-history \
  --branch surviving --until-revision /Users/matkatmusicllc/Programming/jot/common/scripts/plate/plate_cli.py --nth 5 \
  --json --progress > <scratch>/iter1.json 2> <scratch>/iter1.log
```

`--until-revision` takes the FILE path and `--nth` the 1-based ordinal
(`src/reconstruction_cli_args.ts:106`), so both flags name the same file.

### Step 3.3 — commit revision 5 into the scratch clone

From `iter1.json`, take the LAST revision of the target's history. Write its
text (`lines` joined with `\n` plus a trailing newline — the form that
blob-matched in task 182) to
`$SCRATCH/common/scripts/plate/plate_cli.py`, then:

```
GIT_AUTHOR_DATE=<revision.timestamp> GIT_COMMITTER_DATE=<revision.timestamp> \
  git -C "$SCRATCH" commit -am "loop proof: plate_cli.py revision 5"
ITER1_HASH=$(git -C "$SCRATCH" rev-parse HEAD)
```

### Step 3.4 — iteration 2 (re-seeded, bounded to revision 10)

Same command with `--repo "$SCRATCH" --base-commit $ITER1_HASH --nth 10`,
output `iter2.json`. `--repo` may point at the clone because the repo-relative
path comes from the RECORDED cwd, not from `--repo`
(`reconstruction_base_commit.ts:148`), and the clone shares the tree layout.

### Step 3.5 — assertions to report (the actual proof)

Compare the two ladders programmatically (a throwaway node one-liner is fine;
do not add a permanent script):

1. `iter2.json`'s revision 0 `changeId` is `gitBase:$ITER1_HASH:<target>` — the
   re-seed took effect.
2. The set of `changeId`s in `iter2.json` contains at least one NOT present in
   `iter1.json` — history the first iteration did not produce.
3. `iter2.json`'s last revision text differs from `iter1.json`'s last revision
   text — the ladder advanced.
4. Report both runs' wall-clock times and revision counts.

If assertion 2 fails, the finding is real and must be documented as a finding
(not silently retried): record which revisions iteration 2 lost or repeated and
what the cutoff did.
