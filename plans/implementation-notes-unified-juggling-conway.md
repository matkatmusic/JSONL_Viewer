### Design decisions
- **`resolveFilesAtStep(histories, when)` lives in `src/reconstruction_steps.ts`**, beside `produceRepoStateAtTime` — NOT in `viewer_api.ts` as the plan suggested. Signature is `(histories, when)`, not `(histories, steps, stepNumber)`. This avoids a CLI→viewer_api import cycle and the `StepSnapshot` type coupling; both the CLI and viewer already import from `reconstruction_steps`. Range/step-number validation lives in the thin `resolveStepFiles(histories, steps, n)` wrapper in `viewer_api.ts`.
- **The client file-history view renders each revision's content from the revision's OWN `lines`** (mirrors the server's `renderRevisionText`/`linesTextOf`), replacing `computeContentAtTime(steps, path, ts)` which scanned `step.files`. `filesTouched[].revisions[].lines` is already on the wire (verified empirically), so this needs NO wire change and is more rename-correct (the old step-keyed lookup missed pre-rename names). **This is a `.files` consumer the plan's Step 0 grep did not catch** — see Deviations/Open questions.
- **Design B for the build return types (see Tradeoffs):** `buildProjectDocument` and `buildDocumentWithConsent` keep returning the bare `ReconstructionDocument` (zero churn to ~9 passing test files). Two new tuple-returning siblings, `buildProjectReconstruction` and `buildReconstructionWithConsent`, return `{ document, stepFileHistories }`; only the range-patch and step-files routes call them. The `builtDocumentCache` stores the tuple, so histories are cached alongside the document and never serialized onto the wire — exactly the plan's intent.
- **Step 6 measured before building.** Isolated microbenchmark (N=600 distinct spawns, ~12 KB/outcome): persist-after-every-spawn = 3850 ms vs batched(64)+flush = 87 ms → **44× speedup**, pure write-amplification. The O(N²)-write hypothesis is confirmed, so the batching was implemented. Batch size 64, flush at end of `buildReconstructionWithConsent`.

### Deviations
- **`computePatchRoot` now takes `stepFileHistories: FileHistory[]`** and derives the common-directory root from each history's final `target`, instead of scanning `step.files` keys. Same cwd prefix in practice; the s85 `git apply` round-trip test (which validates real relativized paths) passes.
- **`buildStepSnapshots` lost its `target` parameter.** It only fed the removed per-step `files` filter, so it was dead once `files` was gone. Consequence: `reconstruction_cli --json --step N --target X` no longer narrows the printed map to file X — it prints the full repo map at step N. Untested edge combo; the standard `--step N` path is unchanged and covered.
- **Skipped two redundant new tests the plan named.** (a) The synthetic `test_renderRangePatch_diffs_file_text_resolved_from_histories` — the existing s85 `git apply` round-trip in `tests/range-patch.test.ts`, rewired to the new API, already exercises `resolveFilesAtStep` end-to-end far more strongly. (b) The CLI deep-equal `test_reconstructionCli_stepNumber_prints_files_resolved_at_that_step` — it would be a tautology (CLI just calls `resolveFilesAtStep`); the existing `--step` map test + the round-trip cover it.
- **Skipped `test_parseServerArgs_reads_resetSandboxMemo_flag`.** `viewer_server.ts` runs server startup (parse → listen) at import time — importing it in a test starts a server; there is no test seam without restructuring the module. The flag itself is a trivial `argv.includes("--resetSandboxMemo")`. The substantive logic, `resetSandboxMemoOnDisk`, is fully unit-tested (delete + no-op-when-absent).
- **Repurposed, not deleted, the obsolete `test_cli_json_step_files_are_a_plain_object_of_strings`** → `test_cli_json_document_steps_carry_no_file_contents` (asserts the skeleton). Same for `test_convertSnapshotToFileMap_keys_by_path_string` (replaced by the Step 2 skeleton test). Per your "never delete, retire in place" preference I kept them as live regression guards rather than removing.

### Tradeoffs
- **Design B vs. the plan's tuple-everywhere.** The plan had `buildProjectDocument`/`buildDocumentWithConsent` return `{ document, stepFileHistories }`. That is a widely-used public signature — ~11 test files call these (many via `JSON.parse(JSON.stringify(buildProjectDocument(...)))`), so the tuple would have rippled ~40 mechanical edit sites into otherwise-passing suites (including cache-identity and progress tests), each a chance to introduce a real regression. Design B keeps the bare return for those callers and adds two thin siblings for the two routes that actually need histories. Net: 3 test files touched instead of ~11, histories still off the wire, still cached alongside. Cost: two extra one-line wrapper functions.
- **Batched memo persist loses at most one sub-batch (≤64 outcomes) on a hard crash mid-build.** Acceptable: the next cold load simply re-spawns them, and `flushSandboxMemoToDisk()` at end of every completed build persists the tail. The 44× write-amplification win dominates.
